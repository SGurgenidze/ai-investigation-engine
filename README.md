# 🔎 AI Investigation Engine

## პროექტის შესახებ

**AI Investigation Engine** არის დოკუმენტებზე დაფუძნებული კვლევისა და კითხვებზე პასუხის გაცემის სისტემა, რომელიც აერთიანებს ჰიბრიდულ ძიებასა და Retrieval-Augmented Generation (RAG) არქიტექტურას.

სისტემა მომხმარებლის კითხვასთან შესაბამის მტკიცებულებებს ეძებს დოკუმენტებში, იყენებს მათ პასუხის შესაქმნელად და აბრუნებს წყაროებს. თუ საკმარისი მტკიცებულება ვერ მოიძებნა, სისტემა თავს იკავებს პასუხის გაცემისგან.

## ძირითადი ფუნქციები

- დოკუმენტების ტექსტის ნაწილებად დაყოფა (Chunking).
- საკვანძო სიტყვებზე დაფუძნებული ძიება BM25-ის გამოყენებით.
- სემანტიკური ძიება Sentence Transformers-ის გამოყენებით.
- ჰიბრიდული ძიება და შედეგების გაერთიანება Reciprocal Rank Fusion (RRF)-ის საშუალებით.
- ძიების შედეგების გადალაგება Cross-Encoder მოდელით.
- Gemini LLM-ის გამოყენება მტკიცებულებებზე დაფუძნებული პასუხების გენერირებისთვის.
- პასუხებთან დაკავშირებული წყაროებისა და ციტატების დაბრუნება.
- არასაკმარისი მტკიცებულების შემთხვევაში პასუხის გაცემაზე უარის თქმა.
- დოკუმენტების დამატება, ნახვა, განახლება და წაშლა.
- Fixed-size და Sentence-based chunking სტრატეგიების შედარება.
- ავტომატური ტესტირება და ძიების ხარისხის შეფასება.

## გამოყენებული ტექნოლოგიები

- **Python** — ძირითადი პროგრამირების ენა.
- **FastAPI** — backend და REST API.
- **Streamlit** — მომხმარებლის ინტერფეისი.
- **Sentence Transformers** — ტექსტების ვექტორული წარმოდგენები.
- **BM25** — საკვანძო სიტყვებზე დაფუძნებული ძიება.
- **Cross-Encoder** — მოძიებული შედეგების ხელახალი შეფასება.
- **Google Gemini API** — პასუხების გენერირება.
- **Pydantic** — მონაცემების ვალიდაცია.
- **Pytest** — ავტომატური ტესტირება.
- **JSONL** — დოკუმენტების ლოკალური შენახვა.

## მონაცემთა ნაკრები

პროექტის დოკუმენტები ინახება `data/documents.jsonl` ფაილში.

ბოლო შემოწმებით, ფაილში იყო **60,001 ჩანაწერი**, რაც აღემატება 50,000 ჩანაწერის მინიმალურ რაოდენობას.

მონაცემთა ნაკრების აღწერისას აუცილებელია ერთმანეთისგან გაიმიჯნოს:
- მონაცემთა ნაკრების ჩანაწერების რაოდენობა;
- საწყისი დოკუმენტების რაოდენობა;
- ტექსტის დაყოფის შედეგად მიღებული chunks-ების რაოდენობა.

მონაცემთა ნაკრების საბოლოო აღწერაში მიუთითე გამოყენებული წყარო, ლიცენზია და მონაცემების მომზადების მეთოდი, თუ ეს ინფორმაცია ხელმისაწვდომია.

## ძიების ხარისხის შეფასება

პროექტში შედარებულია ტექსტის დაყოფის ორი სტრატეგია:

- **Fixed-size chunking** — ტექსტის ფიქსირებული ზომის ნაწილებად დაყოფა.
- **Sentence-based chunking** — ტექსტის წინადადებების მიხედვით დაყოფა.

შეფასებისთვის გამოიყენება შემდეგი მეტრიკები:

- **Recall@5** — შესაბამისი შედეგის პირველ ხუთ პოზიციაში მოხვედრის მაჩვენებელი.
- **MRR@10** — პირველი შესაბამისი შედეგის პოზიციის მიხედვით გამოთვლილი საშუალო შებრუნებული რანგი.
- **No-answer detection** — კითხვების ამოცნობა, რომლებზეც საკმარისი მტკიცებულება არ მოიძებნა.
- **False acceptance** — შემთხვევები, როდესაც სისტემამ უპასუხა კითხვას, რომელზეც პასუხი არ უნდა გაეცა.
- **False rejection** — შემთხვევები, როდესაც სისტემამ პასუხი არ გასცა, მიუხედავად იმისა, რომ საკმარისი მტკიცებულება არსებობდა.

### ბოლო შეფასების შედეგები

| მეტრიკა | Fixed-size | Sentence-based |
|---|---:|---:|
| Recall@5 | 1.000 | 0.975 |
| MRR@10 | 1.000 | 0.975 |
| სწორად ამოცნობილი no-answer კითხვები | 5/5 | 5/5 |
| False acceptance | 0/5 | 0/5 |
| False rejection | 0/40 | 0/40 |
| No-answer accuracy | 1.000 | 1.000 |

ამ შეფასებაში Fixed-size სტრატეგიამ ოდნავ უკეთესი შედეგი აჩვენა Recall@5-სა და MRR@10-ში.

თუმცა, no-answer ტესტების რაოდენობა მხოლოდ ხუთია, ამიტომ ეს შედეგები არ არის საკმარისი იმის დასამტკიცებლად, რომ სისტემა ყველა ტიპის კითხვაზე თანაბრად საიმედოდ მუშაობს.

შეფასების ხელახლა გასაშვებად:

```bash
python -m evaluation.run_evaluation
```

შედეგები ინახება `evaluation/evaluation_results.json` ფაილში.

## პასუხების სანდოობა და შეზღუდვები

სისტემა პასუხების გენერირებისთვის იყენებს მოძიებულ მტკიცებულებებს და ცდილობს, ფაქტობრივი მტკიცებები შესაბამის წყაროებს დაუკავშიროს.

მნიშვნელოვანი შეზღუდვები:

- შესაბამისი წყაროს მოძიება ავტომატურად არ ნიშნავს, რომ გენერირებული პასუხი სრულად სწორია.
- არასაკმარისი მტკიცებულების აღმოჩენა დამოკიდებულია ძიებისა და შეფასების ზღვრებზე.
- მცირე შეფასების ნაკრები არ იძლევა ყველა ტიპის კითხვაზე განზოგადების გარანტიას.
- Gemini API-ის ხელმისაწვდომობაზე გავლენას შეიძლება ახდენდეს მოთხოვნების ლიმიტები ან სერვისის დროებითი შეფერხებები.
- ლოკალური JSONL ფაილი არ წარმოადგენს მრავალმომხმარებლიანი წარმოებითი სისტემისთვის განკუთვნილ მონაცემთა ბაზას.
- შედეგები პერიოდულად უნდა გადამოწმდეს, განსაკუთრებით მრავალდოკუმენტიანი და ურთიერთსაწინააღმდეგო მტკიცებულებების შემცველი კითხვების შემთხვევაში.
